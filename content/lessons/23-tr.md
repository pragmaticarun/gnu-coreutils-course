`tr` reads stdin, writes stdout, and takes two sets as operands. It does not take a filename. `tr a b file` does not edit `file`. The shell must redirect. `SET1` and `SET2` are lists of bytes, ranges like `a-z`, and classes like `[:upper:]`. `tr '[:upper:]' '[:lower:]'` uses `LC_CTYPE` to decide which bytes are uppercase. Under a UTF-8 locale the class is still not a promise that every Unicode letter maps the way a human expects. The safe mental model is: classes are whatever this libc says they are, and a code point encoded as several bytes is several inputs.

`-d` deletes bytes that appear in the set. `-s` squeezes repeats in the last set down to one. `-c` complements the set. `tr -s 'b'` of `abbac` is `abac`. `tr -d '\n'` joins lines. Those are the everyday uses, and they are the right uses when the data is ASCII or another single-byte encoding you have named.

The failure mode is `é`. The character U+00E9 is the bytes C3 A9. `tr 'é' 'e'` does not mean "replace that character with e". The set contains the bytes of the UTF-8 sequence as the shell passed them. In the capture, translating `é` to `e` produced two `e` bytes: both C3 and A9 were in the set built from the character, and each was replaced. `LC_ALL=C tr` of the same input to `X` produced two `X` bytes. `od -An -tx1` is how you see it. If you wanted a Unicode casefold, you wanted a program that decodes UTF-8. It is not `tr`, and it is not `sed` unless you are in a locale and a sed that actually do that and you have tested the code point.

NUL is a byte `tr` can handle. `tr '\0' '\n'` turns NULs into newlines. That is useful for a quick look and destructive for names that contained spaces and NULs as structure. Prefer `od` or a NUL-aware tool when the NULs were delimiters.

`tr` is not a performance trick for deleting a column. `cut` already does that with a defined field. `tr -d ','` deletes every comma, including ones you needed.

## Worked examples

### Squeeze and downcase

```run
# title: Squeeze b and map ASCII case
/usr/bin/printf 'abbac\n' | /usr/bin/tr -s 'b'
/usr/bin/printf 'A b\n' | /usr/bin/tr '[:upper:]' '[:lower:]'
```

### é becomes two bytes

```run
# title: tr on U+00E9
/usr/bin/printf 'é' | /usr/bin/tr 'é' 'e' | /usr/bin/od -An -tx1
```

### C locale, same split

```run
# title: LC_ALL=C still walks bytes
# env: LC_ALL=C
/usr/bin/printf 'é' | /usr/bin/tr 'é' 'X' | /usr/bin/od -An -tx1
```

### NUL to newline

```run
# title: Make NULs visible as line breaks
/usr/bin/printf 'a\0b\0' | /usr/bin/tr '\0' '\n' | /usr/bin/od -An -tx1
```

## Recipes

Normalize ASCII line endings by deleting `\r`: `tr -d '\r'`. That is the right tool for a CRLF file you are willing to turn into LF, and the wrong tool if some field was allowed to contain a CR.

Squeeze runs of spaces in a log: `tr -s ' '`. Do this only when the run is not significant. A Makefile and an aligned table care about the exact spaces.

## Tips and pitfalls

Ranges `A-z` are not "letters". In ASCII they include the characters between `Z` and `a`. Name the ranges you mean, or use a class and then test it.

`tr` complements with `-c` include almost everything, and the newline's fate surprises people who then join the whole file. Try the command on three lines before you run it on a tree.

Quoting the sets matters. An unquoted `*` in a set is a glob.

## Performance

`tr` is a tight byte loop and it is fast relative to a shell loop that reads one character at a time. It is not faster than `cut` at a job cut defines, and it is the wrong place to look for a speedup if the program behind the pipe is `gzip` or a compiler. Locale classes can make the loop consult the locale tables. For ASCII deletion, `LC_ALL=C` makes the classification byte-simple. Measure before you export it globally; the correctness reason to use `C` is if you want byte identity, and the speed reason is the same shape as the sort locale benchmark: a heavier classification costs more per byte and may still be invisible on a small file in a warm cache.
